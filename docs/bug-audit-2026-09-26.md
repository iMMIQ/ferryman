## P1：优先修复

### B01 — 写入期间取消仍会覆盖源文件

- 位置：[runner.rs:265–290](../src/bin/ferryman_web/runner.rs#L265)，[cancel_job](../src/bin/ferryman_web/jobs_api.rs#L897)。
- 触发：挂载文件选择覆盖保存，在任务进入 `Writing` 后取消。
- 原因：只在进入保存分支前检查一次 cancellation token；保存与最终 `Completed` 更新没有再次处理取消。取消接口此时仍返回成功。
- 证据：隔离测试运行真实 runner，在 Writing 持久化确认处暂停，调用真实 cancel handler 返回 HTTP 200，然后恢复。保存仍执行，源文件被测试输出替换，最终状态为 `Completed`。测试输出为空，因此观察到源文件由 `user original content` 变空；实际任务会写入其生成的翻译结果。
- 修复方向：明确保存提交点，让取消与最终落盘/终态转换协调；接受取消后不得继续覆盖挂载源文件。

### B02 — 领取任务与取消竞争，取消成功后任务重新开始

- 位置：[claim_queued_job](../src/bin/ferryman-web.rs#L469)，[cancel_job](../src/bin/ferryman_web/jobs_api.rs#L911)。
- 触发：数据库 claim 已提交，但 StartingModel 快照尚未写回内存、runner 尚未注册取消 token 时取消。
- 原因：数据库、内存状态和取消 token 的更新没有作为同一次状态转换完成。claim 的旧快照可以覆盖刚写入的 Cancelled 状态。
- 证据：按真实函数的这个交错顺序执行，cancel 返回 200，随后内存状态回到 `StartingModel`，没有已取消的 token 阻止执行。
- 修复方向：统一领取与取消的状态转换，提前注册 token，并在启动前核对权威状态。

### B03 — 自动清理会删除刚重试任务的输入和检查点

- 位置：[sweep_terminal_jobs_at](../src/bin/ferryman-web.rs#L538)，尤其第 550 行删除目录和第 570 行条件删除数据库记录。
- 触发：清理已查出过期终态任务，用户在删除目录前重试该任务。
- 原因：目录按旧查询结果无条件删除；数据库删除的终态条件只能保住已改为 Queued 的行，保不住文件。
- 证据：实际函数交错复现结果为 `status=Queued, DB removed=0, input exists=false`。
- 修复方向：先以事务/互斥方式取得清理所有权，使清理和 retry 互斥，再删除任务目录。

### B04 — 空的批量译文被计为成功，替换模式会丢文字

- 位置：[parse_tagged](../src/translate.rs#L688)，[Engine 批量结果保存](../src/engine.rs#L299)。
- 触发：模型返回正常结束的 `<c1>   </c1><c2>Translated two</c2>`。
- 原因：整段响应非空就能通过验证；每个标签里的文本 trim 后即使为空，仍成为 `Some("")`，进入成功计数与缓存。
- 证据：本地 HTTP 服务返回上述响应，真实 Engine 返回 `UnitDone { attempted: 2, pairs: [(0, ""), (1, "Translated two")] }`，没有把第一段识别为失败。
- 影响：TXT/字幕的 replace 输出将第一段替换为空；覆盖保存时影响源文件。空值还可能进入共享缓存和重试检查点，后续重试不会修复。
- 修复方向：拒绝空标签内容，按缺失译文执行恢复；同时拒绝读取既有空缓存。

### B05 — PDF 连续跨三页的段落漏译第三页及后续内容

- 位置：[merge_across_pages](../src/format/pdf.rs#L898)，[构建可翻译索引](../src/format/pdf.rs#L1022)。
- 触发：一个段落连续跨越至少三页，各页满足跨页合并条件。
- 原因：第二页内容先并入第一页并标记 `merged_up`；处理第三页时又并入已被隐藏的第二页，没有追溯到实际承载译文的第一页。
- 证据：三页最小 PDF 分别含 `Page 1/2/3 paragraph continuation`；解析结果仅一段，内容为第一页和第二页，第三页完全不在待翻译文本中。
- 修复方向：记录跨页段落的真正归属，后续页合并到同一段落。还应保留每页的几何映射，避免 replace 模式下跨页续段原文没有被覆盖。

## P2：Web 和前端

### B06 — 并行保存到同一新目录时部分任务失败

- 位置：[ensure_safe_output_parent](../src/bin/ferryman_web/runner.rs#L35)。
- 触发：多个任务保留目录层级，输出到同一个尚不存在的子目录。
- 原因：检查不存在后直接 `create_dir`，未处理另一个任务已成功创建目录的竞争。
- 证据：生产并行度 8 下调用原函数，7 个任务返回 `File exists (os error 17)`。
- 修复方向：遇到 AlreadyExists 后重新检查目录类型、符号链接和归属，再继续。

### B07 — 批量提交部分生效却整体报失败，重试会重复创建任务

- 位置：[逐文件 enqueue 循环](../src/bin/ferryman_web/jobs_api.rs#L858)，[前端计数与失败提示](../web/src/composables/useSubmission.ts#L315)。
- 触发：目录中前面的文件可复制，后面的文件读取失败；慢网盘复制超时也有相同的“结果不确定”问题。
- 原因：逐文件复制、插入并启动任务，某项失败直接返回 500，不返回已生效任务列表。前端只有拿到完整响应才更新 added。
- 证据：使用项目二进制和真实 HTTP，目录含可读 `a-readable.txt` 与不可读 `z-unreadable.txt`，POST 返回 500 Permission denied，但 GET jobs 已出现前者的 `starting_model` 任务。
- 补充代码证据：前端批量提交沿用 [api.ts:17](../web/src/lib/api.ts#L17) 默认 20 秒总超时，而服务端串行复制完整文件；该超时路径未另做慢网盘实测。
- 修复方向：引入批次/幂等标识，明确返回部分成功结果或把准备阶段与任务发布分离；前端应表达提交结果不确定，避免直接重传。

### B08 — 上传收到无效 2xx 响应仍报成功并清空文件选择

- 位置：[sendFile](../web/src/composables/useSubmission.ts#L241)，[成功计数和移除文件](../web/src/composables/useSubmission.ts#L310)。
- 触发：上传响应为 200 HTML 登录页、空响应，或缺少任务 id 的 JSON。
- 原因：JSON 解析异常被吞掉，任意 2xx 都 resolve；随后仍增加 added 并移除草稿文件。
- 证据：Chromium 中模拟 200 HTML，界面显示“已加入 1 个任务”，`selectedFiles=0`，实际上没有任务。
- 修复方向：校验响应类型、JSON 和有效任务 id 后才能确认成功及移除文件。

### B09 — 两次 active 轮询之间完成的任务可能永远不更新

- 位置：[历史刷新策略](../web/src/composables/useJobs.ts#L24)，[active 差异检测](../web/src/composables/useJobs.ts#L104)。
- 触发：首次历史读取时任务正在翻译，首次 active 返回时已经完成；或其他标签页创建的任务在两次轮询之间完成。
- 原因：历史只在 active 集合发生可观察变化时刷新，空集合到空集合不能发现这些变化。
- 证据：Chromium 复现 `label=翻译中, listReads=1, activeReads=3`；任务已完成但历史不再读取。
- 修复方向：用任务状态版本、有限频率的历史刷新，或核对历史中的未终态任务补足变化。

### B10 — 旧任务详情完成后停留在旧状态

- 位置：[byId 缓存更新](../web/src/composables/useJobs.ts#L96)，[详情数据来源](../web/src/components/JobsPanel.vue#L38)。
- 触发：历史超过一页，打开“进行中”筛选下较旧任务的详情，任务随后完成。
- 原因：任务从 active 和当前筛选结果消失，又不在 all/recent 首 50 条中；byId 只能接收列表返回的行，不能取得这条任务的新终态。
- 证据：Chromium 中 active 已读取 3 次、筛选列表已刷新 2 次且为空，详情仍显示“翻译中 / 0/10”，保留取消按钮且没有下载按钮。
- 修复方向：详情按 id 独立读取，或补取刚从 active 消失的任务最终记录。

## P2：文档处理和 CLI

### B11 — DOCX 文本框导致写出 panic

- 位置：[段落递归收集](../src/format/docx.rs#L108)，[按字节区间写出](../src/format/docx.rs#L180)。
- 触发：外层段落中的文本框含 `w:txbxContent/w:p`。
- 原因：假设所有 w:p 区间互不重叠，实际上文本框段落可以位于外层段落内部；先写外层再写内层导致反向切片。外层还会重复收集文本框文字。
- 证据：最小 document.xml 产生 `BodyTextbox` 和 `Textbox` 两段；写出 panic：`byte range starts at 298 but ends at 239`。Web 的 blocking task 会将其转为任务失败，不是整个 Web 进程必然退出。
- 文本框允许包含段落，可参阅 [Microsoft Open XML TextBoxContent](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.textboxcontent?view=openxml-3.0.1)。
- 修复方向：按结构处理嵌套段落、消除重复文本收集，采用不会重叠的编辑区间。

### B12 — DOCX 使用非 w 命名空间前缀时输出损坏

- 位置：[translated_paragraph](../src/format/docx.rs#L201)。
- 触发：文档使用相同 WordprocessingML namespace URI，但前缀为 `x:` 等，根节点没有 `xmlns:w`。
- 原因：读取按 namespace URI，写入却硬编码 w 前缀且不声明。
- 证据：`x:document/x:p/x:t` 可解析和翻译，输出函数返回 Ok；重新解析输出 XML 得到 `unbound prefix`。
- 修复方向：复用已绑定前缀，或在新增节点显式声明命名空间。

### B13 — DOCX 的换行和制表符被删掉，词语被拼接

- 位置：[parse_paragraphs](../src/format/docx.rs#L115)。
- 触发：段落含 `w:tab`、`w:br` 等文本分隔节点。
- 原因：只连接 w:t，不为分隔元素产生空白。
- 证据：`Hello<w:tab/>world<w:br/>next line` 提取为 `Helloworldnext line`。
- 修复方向：按节点顺序提取段落明文并保留必要的制表/换行语义。

### B14 — EPUB manifest 的 URL 编码路径找不到章节，静默漏译

- 位置：[join_path](../src/archive.rs#L219)，[找不到章节时跳过](../src/format/epub.rs#L46)。
- 触发：manifest 的 href 为 `chapter%201.xhtml`，ZIP 实际成员为 `chapter 1.xhtml`；编码的中文文件名同类。
- 原因：把 URL 当成普通文件路径拼接，没有进行 URL 路径解码。
- 证据：最小 EPUB 得到 `spine item chapter%201.xhtml not found`，最终 `0 content file(s), 0 translatable block(s)`，打开过程仍返回成功。
- [EPUB 规范](https://www.w3.org/TR/epub-33/#sec-item-elem) 将 item 的 href 定义为资源 URL。
- 修复方向：按 URL 语义解析后映射到 ZIP 成员；关键 spine 内容全部缺失时应报告失败。

### B15 — EPUB 明文提取保留实体编码，且吞掉 br 分隔

- 位置：[HTML 文本收集](../src/html.rs#L125)。
- 触发：正文含实体引用，或使用 br 换行。
- 原因：直接拼接 lol_html 的原始 text chunk，没有解码实体，也没有处理换行元素。
- 证据：`Tom &amp; Jerry &lt;3 &#x4E2D;` 原样进入翻译文本；`Hello<br/>world` 提取为 `Helloworld`。模型若原样保留实体字符串，写出阶段还会再转义一次。
- 修复方向：提取实际可见明文，在元素边界补足必要分隔；保持源 HTML 本身不变。

### B16 — PDF 继承间接 Resources 时 replace 写出失败

- 位置：[add_font_to_page](../src/format/pdf.rs#L1657)。
- 触发：页自身没有 Resources，父 Pages 节点通过间接引用持有 Resources。
- 原因：找到继承属性后直接调用 as_dict，没有解引用 Object::Reference。
- 证据：最小 PDF 能正常提取一段文本，replace 写出返回 `page tree has no Resources`。
- 修复方向：对继承资源先解引用，再按页复制并添加字体。

### B17 — Markdown 双语输出复制脚注标识，译文引用指向原文脚注

- 位置：[整块双语复制](../src/format/md.rs#L158)。
- 触发：带 `[^one]` 引用和 `[^one]: ...` 定义的 Markdown 选择双语模式。
- 原因：脚注定义块与普通段落一样复制，原文、译文使用同一个脚注标识。
- 证据：输出含两个 `[^one]:` 定义；用项目锁定的 pulldown-cmark 渲染后出现两个 `id="one"`，两处引用均为 `href="#one"`，无法区分原文和译文目标。
- 修复方向：脚注原文与译文合并在一个定义内，或为译文分配独立标识并同步改写引用。

### B18 — CLI 所有文件失败仍以状态码 0 退出

- 位置：[main 的最终返回](../src/main.rs#L356)。
- 触发：输入不存在、解析失败、写出失败等被收集进 BatchSummary。
- 原因：仅打印 failed_files，最后无条件 `Ok(())`。
- 证据：运行 `target/debug/ferryman --input /tmp/ferryman-audit-core/absent-file.txt --no-cache`，显示 `0 file(s) ok, 1 failed`，进程退出码仍为 0。
- 修复方向：保留批处理继续执行行为，但结束时按失败/取消情况返回合适的非零状态码。

## P2：Agent 和容器生命周期

### B19 — SSE 仍在生成时活动请求计数已归零

- 位置：[ActiveRequestGuard](../src/bin/ferryman-agent.rs#L1231)，[返回流式 Body](../src/bin/ferryman-agent.rs#L1277)。
- 原因：guard 属于 handler，返回 Body 即析构，没有持续到流完成。
- 证据：第一条 SSE 已收到且仍在持续输出时，runtime 返回 `active_requests=0`；释放 lease 后普通 `stop(force:false)` 返回 200/stopped 并中断流。
- 范围：当前 Web 翻译使用非流式请求；这里影响 Agent 的 SSE 调用者。
- 修复方向：让 guard 随响应流持有，在流完成或客户端断开时释放。

### B20 — SSE 关闭总超时的代码无效，190 秒后仍截断

- 位置：[request.timeout_mut](../src/bin/ferryman-agent.rs#L1263)，[Client 默认超时](../src/bin/ferryman-agent.rs#L1344)。
- 原因：锁定的 reqwest 0.12.28 中 Request timeout=None 表示继承 Client 默认值，不表示关闭总超时。
- 证据：检查锁定依赖的合并逻辑，并做等价缩短测试：Client 超时 100ms，服务器每 20ms 发出数据，request timeout=None，仍在约 101.5ms 报 Body TimedOut。生产同一路径继承 190 秒。
- 修复方向：流式请求使用没有总超时的 Client，按需要另设连接/读取约束。

### B21 — CLI 启动容器后健康检查失败，不会清理容器

- 位置：[ContainerGuard::launch](../src/container.rs#L151)。
- 原因：docker run 成功后，健康超时直接 bail；负责 Drop 清理的 Guard 要到健康成功后才创建。
- 证据：fake docker 记录只有初始 rm、run、inspect、logs；CLI 报错退出后 running 标记仍存在。
- 影响：启动过慢或挂起的 vLLM 容器继续占用 GPU/端口。
- 修复方向：docker run 成功后立即建立清理所有权，再执行健康等待。

### B22 — vLLM 父进程退出后遗留 worker，强制停止也无法清理

- 位置：[RuntimeManager::on_tick](../src/bin/ferryman-agent.rs#L740)。
- 原因：发现父进程退出后直接清空 self.child，既未回收进程组，也丢失后续清理所需的组 PID。
- 证据：fake vLLM 启 worker 后 exit(7)，Agent 进入 Failed；force stop 返回 200/stopped 后 worker 仍存活。测试 worker 已清理。
- 修复方向：独立保留进程组身份，异常退出路径也清理整个组。

### B23 — 动态空闲显存被缓存到 Agent 退出，释放显存后仍无法启动

- 位置：[size_launch](../src/bin/ferryman-agent.rs#L566)。
- 原因：GpuProbe::Known 包含 free，后续启动不再探测动态可用显存。
- 证据：模拟 16GiB GPU、首次只有 8GiB 空闲，acquire 报不足；将探测结果改为 16GiB 空闲后再次 acquire，仍显示旧的 8GiB free 并返回 409。
- 修复方向：可缓存静态能力和总量，但每次启动重新获取动态可用量。

### B24 — 损坏或未复制完整的本地模型被标记 Ready，无法直接下载修复

- 位置：[本地模型检查](../src/bin/ferryman_agent/model_manager.rs#L1056)，[Ready 时跳过下载](../src/bin/ferryman_agent/model_manager.rs#L240)。
- 触发：外部挂载/手工复制未完成，或既有模型文件被截断后 Agent 重新扫描。
- 原因：扫描仅要求索引所列 shard 存在且非空，没有验证 safetensors 结构和可用的文件长度/摘要。
- 证据：整个模型目录仅 59 字节，包含 14 字节非法权重，catalog 仍显示 ready；模型目录宣称预期大小为 8,046,402,613 字节。Ready 又使下载接口直接返回成功。
- 范围：正常下载完成路径已有摘要校验，此项不表示所有下载都没有校验。
- 修复方向：扫描时验证安装清单或权重结构；损坏状态应允许重新下载修复。

### B25 — vLLM 能力探测挂起时，启动超时和强制停止都失效

- 位置：[vllm_help](../src/bin/ferryman_agent/gpu_profile.rs#L137)，[runtime 内等待探测](../src/bin/ferryman-agent.rs#L581)。
- 原因：`vllm serve -h`/`--help=CacheConfig` 无截止时间；唯一 runtime 控制循环同步等待它，而启动超時計时在探测之后才开始。
- 证据：fake help 挂起，配置启动超时 30 秒；33 秒后状态仍为 stopped，force stop 请求也超时，但 healthz 返回 200。临时进程已清理。
- 修复方向：为探测设截止时间及进程回收策略，保证异常探测不会永久占住控制循环。
